# MEME Curriculum Delta Handoff
## Required Updates for 101A, 101B, 202A, 202B, and 303

## Purpose

This handoff records only the **delta required** against the current Meme curriculum.

It is not a rewrite of the existing modules.

The current architecture remains:

- **Meme 101A — Foundations**
- **Meme 101B — Survival & Hygiene**
- **Meme 202A — Snipe**
- **Meme 202B — Swing**
- **Meme 303 — Position Management**

The goal is to update each module with the newer concepts developed during the latest review while avoiding duplication between modules.

Add a short section explaining that micro-cap meme trading has similarities with penny-stock trading.

Key points:

- speculative micro-cap behavior is not new
- thin liquidity is not new
- concentrated ownership is not new
- promoter/insider risk is not new
- pump/distribution behavior is not new
- survivorship bias is not new

But micro-tokens are more compressed because of:

- global access
- 24/7 trading
- instant social propagation
- bots
- on-chain transparency
- launchpads
- programmable token mechanics
- rapid migration
- automated copy trading

Suggested line:

> **The speculative behavior is old. The speed, access, and programmable market structure are new.**

Core takeaway:

# 3. Delta Required — Meme 101B

## Current status
101B has the right structure but needs the Thesis Factor and lifecycle refined.

---

## Replace / strengthen: Thesis Factor

Current Thesis Factor should be reorganized around five primary questions.

### 1. Attention Magnitude
How large can the audience become?

### 2. Attention Velocity
How quickly is attention growing?

### 3. Attention Retention
Does attention remain after the first burst?

### 4. Attention Renewal
Is there another reason for attention to return?

### 5. Meta Fit
Is the token aligned with a live or growing meta?

Existing sub-factors such as:

- narrative quality
- X quality
- website quality
- community
- buyer growth
- wallet quality

should remain underneath these five dimensions.

---

## Keep: Hygiene Factor

Current Hygiene structure remains good.

Keep:

- dev wallet
- dev-linked wallets
- bundle concentration
- sniper concentration
- funding clusters
- liquidity control
- sellability
- mint/freeze/blacklist
- contract anomalies
- suspicious historical behavior

Core rule remains:

> **Strong Thesis + Failed Hygiene = SKIP**

---

## Replace lifecycle wording

Replace:

**Start → Burst → Sustained → Plateau → Downtrend → Drained**

with:

**Emergence → Acceleration → Expansion → Maturity → Decline → Exhaustion**

Add:

**Renewal → Expansion**

as the recovery/extension branch.

---

## Add: Meta Lifecycle

Add a second lifecycle:

**Emergence → Expansion → Saturation → Rotation**

Important lesson:

> **A token can be in Emergence while its meta is already in Saturation.**

This should affect expectations.

---

## Add: Three Attention Types

At basic level only, distinguish:

### Organic Attention
Independent discovery and propagation.

### Maintained Attention
Attention kept alive by:
- boosts
- repeated promotion
- raids
- KOL posts
- small support activity

### Fabricated Attention
Bots, wash activity, fake engagement, artificial holder/social counts.

Do not teach sprinkler/KOL inventory mechanics here.

That belongs in 303.

---

## Strengthen: Three Failure Modes

Keep:

### Immediate Rug
Seconds to minutes.

### Slow Extraction / Slow Death
Hours to days.

Separate:

- deliberate slow extraction
- organic attention death

### Self-Rug
Trader converts manageable risk into catastrophic loss.

Add one key principle:

> **You do not need to know whether the token survives forever. You need to know whether its failure mode is compatible with your intended holding period.**

---

## Add: Basic Dev View

Add only enough for pre-trade hygiene:

- dev incentives matter
- visible dev wallet may not represent total dev-linked inventory
- dev may be builder, distributor, or extractor
- repeated deployer history matters
- dev economic alignment can change over time

Do not add detailed Dev Cycle economics here.

That belongs in 303.

# 4. Delta Required — Meme 202A

## Current status
202A is conceptually strong but needs to become more clearly the **early price-formation / Snipe flow module**.

---

## Elevate to core doctrine

Add near the beginning:

> **Snipe reads flow, not levels.**

Explain:

- too little price history exists for mature TA
- the trader is reading live demand and supply
- 180-second bars are compression tools for acceleration, not mature chart structure

---

## Strengthen: Bar Acceleration

Make bar acceleration central.

Monitor:

- transaction frequency
- buy frequency
- sell frequency
- average buy size
- average sell size
- unique buyers
- holder growth
- liquidity consumption
- speed of dip recovery
- sell impact
- buyer persistence

Teach:

**momentum = sustained activity**

**acceleration = activity increasing in strength or speed**

Core idea:

> **Snipe tries to detect acceleration before the chart makes it obvious.**

---

## Add: Attention Conversion Chain

Explicitly teach:

**Attention**
→ **Unique Buyers**
→ **Capital**
→ **Available Supply Consumed**
→ **Price Response**

Then add:

### Conversion Efficiency

Ask:

> How much new buyer/capital response does additional attention produce?

Example:

Early:
- 100 mentions
- many new buyers
- strong price response

Later:
- 1,000 mentions
- few new buyers
- weak price response

Interpretation:
attention may still be high, but conversion efficiency is falling.

---

## Add: Token LC vs Meta LC

Teach that token lifecycle and meta lifecycle can diverge.

Example:

Token:
**Emergence**

Meta:
**Saturation**

Meaning:
the token is new, but the trade may already be late.

---

## Add: Migration Event Cycle

Add a section:

### Pre-Migration → Migration → Post-Migration

Teach that migration itself can contain a complete attention lifecycle:

**anticipation**
→ **acceleration**
→ **event**
→ **plateau**
→ **renewal or sell-the-news**

Important lesson:

> **A successful event can still mark the top if there is no next reason to buy.**

---

## Add: PVP Dominance & Rotation

Teach:

> **PVP may have no official winner at the beginning.**

Practical process:

**enter strongest current candidate**
→ monitor competitors
→ compare legitimacy / attention / flow
→ stay if dominance persists
→ rotate if a materially stronger candidate emerges

Important rule:

> **The first token does not need to fail before capital rotates.**

---

## Add: KOL Coordination in PVP

Teach three KOL advantages.

### Case A — Recognition Edge
KOL identifies the objectively strongest candidate early.

### Case B — Coordination Edge
No objective winner exists yet.

The KOL:
- enters one candidate
- followers react
- copy traders follow
- another KOL may cross-confirm
- holder quality can improve
- one token becomes the focal point

The KOL may profit from the first candidate even if it later loses the PVP.

### Case C — Rotation Edge
A stronger token appears.

The KOL:
- detects faster
- cuts or reduces old candidate
- moves into stronger narrative-linked token
- crowd catches up later

Core lesson:

> **KOL action can be discovery, coordination, or rotation.**

---

## Add: KOL Synergy

Teach that a KOL may check:

- whether another KOL is already in
- whether known smart wallets are present
- holder composition
- wallet concentration
- competing-token momentum

Multiple respected participants can help create market focalization.

---

## Keep unchanged

Retain:

- price as auction
- liquidity / price impact
- buy/sell pressure
- supply transfer
- early wallet flow
- momentum / acceleration
- attention → capital
- Push / Hold / Fail

These remain valid.

---

## Elevate to core doctrine

Add near the beginning:

> **Swing reads structure, then verifies flow.**

Structure tells the trader where to look.

Flow decides whether the area is valid.

---

## Add: Fibonacci / Retracement References

Add explicit section.

Teach:

### 0.5
Midpoint reference.

### 0.618
Fibonacci retracement reference.

Important:

- neither predicts reversal
- neither should be bought mechanically
- they help define areas where fresh risk may be reconsidered

Core line:

> **Fib gives the area. Supply/demand behavior decides the trade.**

A stronger Swing setup is:

**reference zone**
+ **seller exhaustion**
+ **absorption**
+ **renewed buyers**
+ **thesis persistence**

---

## Strengthen: Attention Persistence

Swing should monitor:

- does discussion survive quiet price periods?
- do buyers return after pullbacks?
- does the narrative regenerate?
- are new wallets still arriving?
- does a new catalyst renew the LC?
- is the meta still alive?
- has attention moved to competitors?

Key distinction:

**Base Formation**
vs
**Dead Token With Trapped Holders**

---

## Add: Market Maturity Transition

Teach three market states.

### Stage 1 — Launch / Micro-Cap
Dominant information:

- attention
- wallet flow
- dev
- bundles
- snipers
- liquidity

### Stage 2 — Established DEX
Now add:

- price structure

- BTC direction
- ETH / SOL beta
- funding
- open interest
- order books
- market-wide liquidity
- smart-money concepts
- broader TA / liquidity sweeps

Core principle:

> **As market maturity rises, information and liquidity usually improve while asymmetry declines.**

# 6. Delta Required — Meme 303

## Current status
303 already contains most of the new position-management logic.

The main outstanding addition is the **Dev Cycle / Buyer Cycle model**.

---

## Add: Token as a Two-Sided System

Teach that every token has at least two views:

### Buyer / Trader View
Why will people:

- discover
- buy
- hold
- add
- rotate
- exit?

### Dev / Team View
Why was the token created?

How does the dev/team benefit?

How do they:

- build
- market
- monetize
- distribute
- reinvest
- exit?

---

## Add: Dev Cycle

Use:

**Create**
→ **Launch**
→ **Market**
→ **Improve**
→ **Monetize**
→ **Reinvest / Exit**

Do not imply every dev follows the same path.

This is an analytical cycle.

---

## Add: Buyer Cycle

Use:

**Discover**
→ **Assess**
→ **Enter**
→ **Monitor**
→ **Add / Hold / Exit**
→ **Reassess**

---

## Add: Shared Interaction Layer

Between Dev Cycle and Buyer Cycle sits:

- Narrative
- Attention
- Liquidity
- Price
- Volume
- Fees
- Holder growth

Core idea:

> **Price emerges from the interaction between the Dev Cycle and Buyer Cycle.**

---

## Add: Three Dev–Buyer Relationship States

### Alignment
Dev keeps building / promoting.

Buyers keep arriving.

Attention renews.

Positive reinforcement can continue.

### Divergence
One side remains committed while the other weakens.

Examples:

- buyers still believe while dev distributes
- dev still builds while market attention has already left

### Extraction
Buyer demand increasingly funds insider/dev monetization without enough reinvestment or renewed value creation.

This can resemble planned slow extraction.

---

## Add: Dev Economics

Teach defensively:

- creator fees
- transaction fees
- token inventory
- treasury
- LP economics
- product/service revenue
- marketing budget
- creator incentives
- repeated launches

Do not assume fee income means alignment.

---

## Add: Transaction Fee Explanation

Teach that a token-specific 3% transaction fee is separate from DEX/launchpad trading fees.

A token may route the fee to:

- dev / treasury
- marketing
- liquidity
- burns
- holder rewards
- other destinations

The trader should understand:

- who receives it
- whether it applies to buy/sell/both
- whether it changes
- whether it meaningfully affects exit economics

---

## Add: Dev Inventory vs Visible Dev Wallet

Teach:

> **The visible dev wallet is an address. The economic dev position may be a network.**

Defensive analysis can examine:

- deployer funding
- direct transfers
- linked wallets
- common funding
- synchronized activity
- repeated destinations
- cluster behavior

Do not provide evasion instructions.

---

## Add: Dev Types as Behavioral Spectrum

Do not make rigid labels.

Use a spectrum:

### Builder
Primary value comes from:
- building
- sustainable fee/revenue
- continued ecosystem growth

### Builder + Distributor
Builds while also monetizing inventory / fees.

### Extractor
Primary behavior is:
- attention creation
- fee capture
- inventory distribution

### Serial Scammer / Repeated Extractor
Repeated historical launch / extraction patterns.

The goal is to understand incentives and behavior, not moral classification from one transaction.
