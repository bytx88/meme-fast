# Meme Fast

Meme Fast connects emerging crypto narratives with observed token activity. Its research flow moves from public-source discovery to narrative evidence, exact contract associations, and recent swap analysis.

## Run locally

Requires Node.js 20 or newer. Robinhood pool indexing also uses Python with `httpx` and, on Windows, `truststore`.

```sh
py -m pip install httpx truststore
node preview.mjs
```

Open `http://127.0.0.1:4173/narratives.html`.
The local preview indexes Robinhood pools into `.data/robinhood-pools.sqlite` on each collection run. The public RPC is rate limited, so historical coverage builds gradually. Set `ROBINHOOD_RPC_URL` to a suitable archive endpoint when available to accelerate backfill.

## X social signal

Tweet and Swing show an **X RSS** badge for each sampled contract. It counts x.com posts indexed by Google News RSS in the current six hours and shows the change versus the previous six hours. The inspector links to indexed items. A zero means none appeared in this RSS sample; it does not mean there were no X posts. The count does not include likes, reposts, author diversity, or a 0–100 X Factor score, and it does not affect market rankings.

The collector in [x_rss_collector.py](worker/x_rss_collector.py) queries the exact contract and up to three configured aliases in a 12-hour RSS window. It deduplicates items, requires an x.com source, and withholds a target when a query reaches the 100-item result cap. It prioritizes [e/acc, PAID, and XLINK](x-factor-targets.json), then high-buyer market coins. e/acc uses its exact contract because the name also describes a broader movement; PAID adds UsePaid, and XLINK adds its project domain and handle. These aliases require manual contract association.

`/api/x-factor` reads `/history/x-factor.json` on Modal or `.data/x-factor.json` locally. Its RSS report is marked `source: google-news-rss`. Modal refreshes the three priority targets every 30 minutes, and badges become stale after 45 minutes. Run `collect_x_factor` manually on Modal or `py worker/x_rss_collector.py .data/coins.json .data/x-factor.json x-factor-targets.json` locally. The deployed RSS collector needs no X API key.

The earlier [XFlux](https://www.xfluxapi.com/docs/api) collector remains in [x-factor-collector.mjs](worker/x-factor-collector.mjs) for manual experiments. Its initial live pilot returned matching posts without author identities, so the account-diversity score was withheld. The paid official X collector also remains an explicit local option. Neither is used by the deployed RSS function.

The current app uses public data providers, shared retained observations and browser storage for personal research state. See [ARCHITECTURE.md](ARCHITECTURE.md) for the shared token/wallet stream, source ownership and application boundary.

## Shared data stream

Tweet, Snipe, Swing, Watchlist, Inspect and Smartness reuse common collected evidence. On Modal, GeckoTerminal, DexScreener, Solana RPC and indexed-X RSS each have a shared source owner for caching, pacing and cooldowns. Overlapping token batches fetch only missing contracts; complete wallet scans can supply token-balance cohorts without repeating wallet-by-token RPC calls. Tweet reads the scheduled publisher/trending snapshot rather than fetching those feeds in each browser.

`GET /api/data-stream?window=5m|1h|6h|24h` provides trending tokens, largest observed holders and recent accumulators. Older launches remain eligible when recently active. The response publishes its criteria, coverage, original observation times and stale state. Token discovery can nominate holder wallets, and recent wallet buys can nominate token lookups, with bounded admission and no automatic SmartMoney promotion. Rankings use measured provider windows, not sums of overlapping samples. Holder coverage is sampled; a holding increase alone does not establish a buy. `GET /api/data-stream/sources` reports committed source-cache counters; these are cache hits/misses, not a claim of complete upstream-provider accounting.

The pool is capped at 60 tokens across the four windows and 100 discovered wallets, with two holder-discovery targets per pass and up to 30 wallet-led token candidates per market run. Current pool and Interested wallets have five-minute refresh targets; other saved SmartMoney wallets use 30 minutes and other saved wallets one hour. New wallets get an initial check. Quiet markets reduce or leave routine refresh; retained history remains available and new activity or Inspect can resume collection. Public-provider capacity can delay every target. Wallet feeds currently cover Solana.

## Followed wallets

The scheduled holdings sampler has a 180-second RPC budget inside a separately enforced 210-second subprocess deadline; its 480-second Modal limit leaves room for registry access and Volume reload/commit. Each token-program request and pacing delay respects the remaining sampling budget. A partial wallet check preserves its previous complete holdings. A stuck subprocess is killed and reaped before returning a failure, and its output is never committed as a successful run. ## Trust and freshness

The collector refreshes up to 1,800 retained contracts per run alongside discovery: saved refresh interests first (up to 300), then the Swing universe, recent discoveries, and older contracts rotated by last refresh attempt. Saving a supported token or opening Snipe, Swing, or Watchlist requests 24-hour refresh priority for contracts already in the retained sample. This sends contract IDs only; the watchlist itself remains browser-local. Unknown contracts use manual lookup and are not silently added to scheduled collection. The shared priority queue does not guarantee a fresh provider response.

Provider requests are paced and start their timeout after leaving the queue. A rate-limited request waits for the provider cooldown and retries once when the collection budget allows; longer cooldowns preserve the last snapshot and survive collection runs. Discovery covers the first new-pool page of every chain, then checks launchpad progress for up to 200 retained and newly discovered contracts before dedicated Pump.fun/Meteora DBC discovery, trending feeds, tracked/indexed Robinhood pools and deeper pages can consume the provider budget. New pairs receive the first 80 of 120 check slots, followed by up to 20 known Final Stretch coins and an oldest-checked rotation for the remaining slots. Up to 80 additional check slots cover retained active launchpad pools and up to 30 saved refresh interests, ordered by pool liquidity; this does not assign graduation status. New dedicated-pool discoveries enter the following scheduled graduation pass. Pump.fun page one is checked every run, and pages 2–9 rotate over two runs; Meteora DBC page one is checked every run. Active launchpad pools can enter discovery even when older than 36 hours. Token checks include exact-token top pools so current curve liquidity comes from pool reserves instead of an absent Dexscreener field. These jobs run on the five-minute Modal schedule independently of page visits. Missing graduation coverage is shown as unavailable rather than a measured absence of Final Stretch coins. Retained market refresh proceeds independently; context has a separate bounded time window. A bounded request/time budget preserves retained snapshots when providers are unavailable. The Robinhood indexer runs alongside market collection, using its last atomic export for this run. Freshness is measured per token, separately from the collection timestamp: Snipe uses six minutes and Swing/Watchlist use fifteen. Missing current liquidity or volume stays unknown. Swing withholds displayed research scores for stale or incomplete market data.

Snipe classifies launch lifecycle before price patterns: measured progress below 80% is New Pairs; 80% or above without confirmed completion is Final Stretch; provider-confirmed completion is Graduated. Axiom’s public Pulse guide describes near-completion without specifying a threshold, so 80% remains an explicit Meme Fast rule. The left column stacks Final Stretch above Fresh Pairs. The middle Observed recovery column retains 45m A rebound / B continuation, later recovery, and confirmed graduations under observation. Recovery is an independent view: qualifying coins can appear there and in their launch-stage section, so a recovery never removes a coin from Final Stretch. The right Pool activity column separates confirmed graduation from volume-only evidence. Unknown graduation status and volume-only candidates are listed separately. Final Stretch spans the retained five-day sample, independently of the selected discovery window; Fresh Pairs keeps that window. The compact screener has Common, New Pairs, Recovery, and Graduation tabs. Common minimums and chain apply to Discover and Explore; each column tab adds its own 24h volume, liquidity, 5m volume, and transaction minimums in Discover. Every tab also includes minimum and maximum pool age in seconds and a lifetime pool transaction minimum. Lifetime transactions use reported 24h buys plus sells only for pools younger than 24 hours, whose lifetime fits inside that window; counts for older pools or missing data stay unavailable and fail a positive minimum. Zero disables an age limit or lifetime minimum. New Pairs defaults to a maximum pool age of 108,000 seconds (30 hours); existing settings without an age cap receive this default, while an explicitly saved zero stays off. Settings tabs show the number of active criteria, such as New Pairs (1). Zero disables an extra minimum. New Pairs settings also cover Final Stretch and unknown-status rows; Graduation settings cover confirmed graduations and volume-only rows. Recovery settings apply independently, preserving coins in other qualifying columns. Settings persist in this browser. Observed recovery describes a historical pattern. The drawdown/rapid-rise filter is a price-pattern filter, not a contract-safety test. Existing `radar.html` links and saved `radar` items continue to work under the Swing name.

For isolated UI checks, `PORT=4182` selects another preview port and `MEME_COLLECTOR_DISABLED=1` serves existing `.data` snapshots without starting collection.

## Shared Market Delta

The shared header displays a 1-hour Meme Delta and broad-alt Delta around zero. `collect_meme_index` samples them every five minutes on the persistent Volume, and `/api/meme-index` serves the public readings. Meme Delta is the equal-weight mean of one batched DexScreener request's 1-hour price changes for the 10 liquid exact-contract FOMO Most Held constituents. Alt Delta is the market-cap-weighted 1-hour change of the 25 largest eligible non-BTC/non-ETH altcoins from one bounded CoinLore top-50 request. Stablecoins and wrapped assets are excluded. The first complete reading is immediately displayable; later readings build the chart. Missing one-hour changes withhold a reading rather than becoming zero.

Only the collector receives the `meme-fast-fomolist` Modal secret (`FOMO_KEY`). FOMO Most Held is read at most once every 72 hours, including failed attempts; price sampling and page visits never call it. The initial authenticated September 29 leaderboard response is saved as a seed to avoid another FOMO read at startup. Every three days the collector freezes 10 eligible exact contracts and saves a membership snapshot. The separately stored compounded Meme Index starts at 100, retains its level across rebalances, and begins at collection without historical backfill.

Routine market sampling uses one batched meme request and one bounded alt request every five minutes. The chart compares reported 1-hour changes sampled at each collection, so it does not claim a continuous trade tape. Local preview reads `.data/meme-index.json`; run `py worker/meme_index.py .data/meme-index.json` explicitly to sample locally (future rebalances require local `FOMO_KEY`).

### Scheduled collector reliability

`collect_coins` accepts one input at a time, with a 540-second overall deadline below Modal's 600-second execution limit. Reload, priority lookup, collection, projections, shutdown and commit have separate budgets. Volume reload allows 90 seconds, commit allows 120 seconds, and checkpoint/health I/O allows 30 seconds to tolerate transient storage congestion. Provider collection remains capped at 280 seconds. Cancellation does not wait indefinitely for an RPC to acknowledge it. Subprocess output goes to temporary files instead of pipes; Linux process groups are killed during bounded cleanup, including descendants whose parent has already exited. Every writer must stop before the Volume is committed.

A collector timeout is recoverable only when this invocation saved a valid fresh atomic snapshot. That snapshot is projected and committed with a `degraded` health report. Optional indexer, priority and projection failures are recorded; an old snapshot, a collector crash, a failed shutdown, or an unsuccessful Volume commit remains a real function failure. Provider errors stay visible and never become invented fresh observations. Degraded runs return normally, so they do not trigger Modal's failed-function digest. Real failures still trigger the existing provider notifications; notification preferences are unchanged.

`/api/collector-health` reads the durable `coin-job-health.json` report: design version, stage outcomes, warnings, provider errors, snapshot revision, last successful run and consecutive failed runs. It returns HTTP 503 for failed, missing or more-than-15-minute-old reports, and 200 for recent complete or degraded runs. Reload/commit failures cannot reliably publish a new report, so stale health remains an independent sign of trouble. Modal digests cover previous failures and can still arrive after recovery.

### Smart history backfill

`worker/smart_backfill.py` reconstructs the complete transaction histories of the currently discovered HOOKED token accounts. Every account must reach its initialization, have continuous integer pre/post balances in slot and transaction order, and reconcile to its finalized current balance. A missing transaction, ownership/decimal mismatch, truncated signature page or discontinuity rejects the group. Version-1 transactions are supported. Histories are projected to five-minute balance states; prices are actual hourly GeckoTerminal closes timestamped at candle end, with no invented pre-market prices. The nine current accounts may omit additional historical closed or non-associated accounts; this limitation is visible under Historical coverage. This fixed group does not reproduce Nansen's broader Smart Money cohort, including exited wallets.

Collect or resume public evidence, then validate the artifact:

```powershell
py -m worker.smart_backfill .data/smart-backfill .data/smart-backfill/payload.json --collect
py scripts/import-smart-backfill.py .data/smart-backfill/payload.json
```

Only when the history write is authorized, after deploying its code, apply the artifact with `py scripts/import-smart-backfill.py .data/smart-backfill/payload.json --apply`. This calls the existing single-writer `collect_smart_wallets(backfill=...)` through authenticated Modal access using profile/workspace `bytx24`. There is no public history-write endpoint. Group/range/raw-balance validation runs before writing; imported history precedes the earliest live observation, preserving every observed snapshot. Collection retains the history and its source metadata. No raw transaction cache, local database or secrets are uploaded. Public RPC can rate-limit archive reads; cached immutable transactions survive retries. An authenticated RPC may be selected with `SOLANA_WALLET_RPC_URL`.

Inspect separates **Flow** (sampled buy/sell activity) and **Balance** (token holdings) tabs. **Smart*** filters Flow to the shared universe; Balance selects the original nine-wallet HOOKED group, the Smart universe, or Interested Parties for any single Solana mint. Smart Flow filters exact swap sender addresses and retains sample coverage notices; aggregate pool candles are never presented as Smart flow. The All-wallet Balance view explicitly reports unavailable coverage and offers the Smart filter. New token/group histories begin with observations; membership changes use a separate identity and never reinterpret the existing curve. Switching tabs retains the filter.


### Wallet universe and Interested Parties

`/admin.html` is the research-admin home linking Sources / X Accounts and `/smart-wallets.html`. The Smart Wallet universe merges the existing tracked-wallet registry (13 seeded Interested Parties, plus prior additions), the nine user-supplied Nansen wallets, and durable overrides/additions in Modal Dict `meme-fast-wallet-universe`. Membership is deduplicated by exact Solana address. Interested is independent of source and class; editing/unflagging does not remove a wallet. Source labels are user-entered provenance, not verified profitability.

`GET /api/wallet-universe` returns identity, metadata and last complete holdings coverage. POST adds a wallet; PATCH edits metadata or toggles Interested. Optional class keeps existing F/C/N/L/Dev tags. The existing five-minute collector samples the shared universe, prioritizing current-pool and Interested wallets, then least-recently attempted due wallets, with a 180-second RPC work budget. Large universes rotate across runs; unsampled wallets retain their actual timestamps and become visibly stale. `GET /api/followed-wallets` projects only Interested entries for Snipe and Swing; unclassified Interested entries receive the generic I / Interested Party tag. Previously observed holdings are retained across failures; new entries await a scheduled check. No deployment-time registry migration or reset is performed. The local preview stores its own overrides in ignored `.data/wallet-universe.json`.

Smart Flow reads this shared registry for any single Solana listing. Balance preserves the original nine-wallet HOOKED curve, while other Solana tokens can start separate Smart-universe or Interested-only histories. Membership is sorted for stable identities; changes create a separate file. Actual token decimals are read on chain before balances are interpreted. Failed checks preserve stale individual balances and create aggregate gaps. Opening a group registers it for scheduled rotation for 24 hours; the single writer samples the least-recently checked active group alongside the original group. Multiple active groups rotate, so their observation interval may exceed five minutes.

The Top wallets section analyzes a chosen universe wallet on demand via `GET /api/wallet-activity?address=...`. Public Solana RPC provides at most eight recent owner-address signatures, limited to the past 24h, plus transaction metadata with version 1 support. Results are cached per web container for five minutes; the UI ranks only wallets analyzed in the current session by swap-associated receipt count. Raw token deltas aggregate all accounts for the owner. A recognized swap instruction log plus a positive token delta is labelled Swap-associated receipt, which can include unrelated transfers; other deltas are Received / unclassified. This does not establish exact buys, USD volume, profit or complete wallet activity. Missing transactions and RPC rate limits are explicit, and uninspected activity remains unknown. No Nansen API, Fomo API or paid provider is used.


### Smartness flow rankings

The Smartness page (`smart-wallets.html`) now has Wallet universe, Top wallets and Top tokens views. Wallet/token rankings use one shared time window (1h, 24h, 7D or 30D), quote currency (SOL, USDC or USDT), source and Interested filter. Buy minus sell is net buying, not PnL. Cross-links drill from a wallet to its tokens or from a token to its participating wallets. All displayed sums derive from the same deduplicated ledger. No current-price or assumed stablecoin/USD conversion is applied to historical flows.

`worker/smartness.py` recognizes explicit instruction discriminators for the known Jupiter, Pump and PumpSwap programs from `worker/smartness-programs.json`. The whitelist contains primary-source IDL links and finalized-transaction evidence for Jupiter v2 names/discriminators. A supported direct instruction must have an owner signer, attributable token transfers inside its CPI scope, one non-quote asset moving opposite one supported quote asset, and a token quantity reconciling to the owner's actual pre/post balances. Temporary initialized wrapped-SOL accounts are mapped explicitly. Native SOL amounts use System transfer instructions inside the swap; network fees and account creation rent are excluded. Unknown programs/discriminators, CPI-only outer routers, token-to-token routes, transfers, ambiguous quantities and failed transactions do not become trades.

The single-writer `collect_smartness` function stores a 30-day ledger in the separate Modal Volume `meme-fast-smartness-ledger`, retaining up to 50,000 instructions. It shares the existing five-minute dispatch job (no additional schedule), has a four-minute cooldown, a 190-second scan budget, and rotates least-recently-attempted wallets. Each scan decodes up to eight recent plus eight historical transactions per wallet. A durable backward cursor and unfinished page advance toward the 30-day boundary; missing transactions remain queued before that page advances. A daily head restart revisits the moving window. Public provider boundaries do not prove a complete archive, and high recent activity can exceed the head sample. Seen signatures prevent repeated work and event IDs prevent duplicate flow. Historical evidence survives failed refreshes and metadata changes. GET `/api/smartness` omits internal seen/history queues; POST `/api/smartness/refresh` requests a bounded scan. The original nine-wallet Balance history remains unchanged.

Existing verified public transaction evidence from the earlier requested backfill can be replayed with `py scripts/replay-smartness.py .data/smart-backfill/transactions` for local inspection. The script verifies filenames/signatures and re-runs the same decoder within the 30-day retention window. Only `--apply` writes classified evidence through the authenticated single-writer Modal function using bytx24. No public import endpoint exists and raw caches are excluded from deployment. New trade samples come from public Solana RPC only; the public DEX Screener token endpoint optionally supplies exact-mint display symbols and never supplies historical flow values. These are observed flow rankings, not a complete blockchain archive or guaranteed smart-trader performance scores.

### Public discovery and imports

Smartness has a Discover / import tab. It loads up to 15 distinct Solana base tokens from the public GeckoTerminal trending-pools feed, or accepts up to 15 pasted contracts. Public Solana largest-account queries and parsed account resolution identify up to 10 distinct signing-wallet candidates from 20 token accounts per mint. Off-curve program authorities and executable/non-system-owned authorities are excluded. Balances cover sampled accounts, not complete owner holdings. Candidates are unverified holders; adding one uses source Public and an optional Interested flag. Results cache for five minutes per container, with a 200-token limit. Public providers can reject indexed holder requests; these errors remain visible.

Nansen/Fomo lists can be pasted into a previewed bulk import (up to 150 addresses). All addresses validate before writes; duplicates and existing entries are skipped without changing metadata or Interested flags. Partial write failures are reported per address. Source labels record supplied provenance, not verified profitability. No paid API or automatic extraction of Nansen/Fomo Smart Money labels is configured.

History/discovery reads use paced public Solana endpoints (mainnet-beta and PublicNode), bounded fallback and per-method cooldowns. A configured SOLANA_WALLET_RPC_URL overrides this pool. PublicNode may require personal access for indexed holder requests; the app does not bypass that restriction.

Inspect Flow/Balance totals, token prices, holdings, trade quantities, chart values and Smartness rankings share magnitude-based rounding through smart-number.mjs: maximum 4/5/6 decimals at absolute thresholds 10/1/0.01, scaled six-decimal e-N notation below 0.01, trailing zeros removed, and zero displayed as 0. Ledger quantities remain unchanged.


### SmartMoney and wallet classification

`smartMoney` is an independent nullable boolean: Yes (`true`), No (`false`), or Unreviewed (`null`). Inspect Smart filters, balance cohorts and Smartness ranking filters use this saved flag, not source or classification. `smartStatus` is a compatibility description derived from this flag. Classification (`code`), multi-source provenance (`sources`) and Interested remain separate. Editing a class/source does not change SmartMoney. New wallets and public holder candidates default to Unreviewed; bulk imports have an explicit SmartMoney selector.

The authorized legacy migration sets L1/L2 (long-term holder classes 1/2) to Yes, and F1/F2, N1/N2, C1/C2 and S1/S2 to No. C1 means fast clipper/sniper; C2 means slower clipper/sniper. Cupsey-related wallet names remain intact. Existing approved Nansen/Fomo eligibility is preserved during migration only; new source labels do not promote wallets. Preview with `py scripts/migrate-smart-money.py`, then apply the authorized conversion with `--apply` on profile/workspace bytx24. The script saves a local backup, skips reviewed flags, checks concurrent edits and verifies all other stored metadata is unchanged.

A reduced balance cohort can reuse saved raw per-wallet observations from a strict superset of the same token. Each point is recalculated for the exact remaining addresses; any missing member keeps that point incomplete. Original history files remain intact. This does not reconstruct unobserved dates. Automatic top-token seeding and dormancy are described below.


### Automatic SmartMoney token collection

Inspect's search suggestions filter known names, tickers and addresses locally. A compact `view=catalog` projection reuses the retained Snipe/Swing collector lists; browser-cached catalogs, watchlist entries, recent Solana tokens and Inspect snapshots supply immediate matches. The catalog preloads when Inspect opens, with no market-provider requests while typing. The collector atomically writes `coins.catalog.v2.json` alongside its other projections, so subsequent reads avoid loading full market histories. Results retain chain and exact contract identity, support arrow keys/Enter/Escape, and open one selected listing. Exact names/tickers rank first; equally relevant matches sort by holder count, then 24-hour volume, then market cap, descending with unknown metrics last. Available figures appear in each suggestion. Unmatched submitted queries continue through the existing public lookup.

`worker/smart_seeding.py` ranks valid, observed tokens from the retained 24-hour swap ledger using only current `smartMoney=true` wallets. Weights are distinct buyers 40, Interested buyers 25, positive net quote flow 15, new holders 10 and recency 10. Counts are normalized against candidates. Net flow is normalized independently inside SOL/USDC/USDT; the strongest positive component contributes without adding unlike currencies. New holders require complete recent and nearby day-ago raw balance snapshots. Unknown growth remains unmeasured and contributes no score. This is research priority from a partial trade sample, not a performance or safety rating.

The top 20 in the measured active pool are enrolled automatically; if fewer qualify, the queue does not fabricate more. The existing five-minute dispatcher uses a single durable lease for all scheduled and Inspect collection, preventing repeated scheduler jobs from building a backlog. The single balance writer loads the trade ledger and recent wallet holdings read-only, publishes its plan/checkpoints to the existing Smart Volume, and finishes one cohort per job (900-second budget). Reserved turns serve Inspect, ranked seeds and retained monitoring. Due targets: 15 minutes for Inspect, four hours for top-20 tokens, daily for former seeds still in the current activity stream. Tokens outside a measured active pool pause routine balance collection until new activity or Inspect interest; saved history remains intact. Capacity and public-provider failures can delay these targets; all data, retries, last complete checks and due times are visible in Smartness → Collection queue. Inspect visits register an interest even in Flow mode. No historical dates are invented; general archive backfill is not included.

The ten-day pause policy requires complete exact-membership raw-zero snapshots on every UTC date in a consecutive run and at least ten elapsed 24-hour periods. Repeated observations on one date do not create extra days. Missing dates break the run; partial or unavailable reads never certify zero. Positive raw balances, including partial observations, and observed SmartMoney buys invalidate their date. Membership changes reset the evidence, and subset-derived chart history cannot backdate the pause clock. Evidence is stored independently of chart retention in `collection-plan.json`. Dormant tokens retain history and receive weekly balance probes. Fresh positive SmartMoney holdings scans, new SmartMoney buys and subsequent Inspect visits resume collection. Holding scans can detect receipts/transfers, but this is not an instant transfer subscription. Scope-limited Interested or original-nine snapshots cannot certify a zero full-universe balance.

`GET /api/smart-seeding` exposes ranking, score components and collection state; `POST /api/smart-seeding/refresh` requests one deduplicated job. The single writer owns plan/history writes. Preview/refresh requests do not delete history or change wallet eligibility. The existing original-nine HOOKED history remains archived and follows any token-wide dormancy decision.

Newer positive activity takes precedence over older zero snapshots replayed afterward. Promotion into the top 20 shortens an existing daily deadline to the four-hour cadence. Incomplete or failed dormant probes retry after five minutes; only a complete probe starts the next weekly interval, and positive probes resume the token's active cadence.
